# 外部计划评审（2026-10-26）：「25 个 skills」模块清单逐项裁定

来源：用户转发的另一 AI（Claude）为织界设想的产品模块清单（25 项，★ 标 3/6/16/23 为决定性模块，并自评核心链路为「设定圣经 → 写章节 → 一致性检查 → 存进 DAG → 可视化」）。
本文件是主助手的逐项分析存档。裁定口径：以织界**现行产品模型**为准——AI 生成的季播爽文（24 章一季 + 章末选择 + 双人合流），不是 UGC 无限分支平台。凡清单中以「无限公开分支」为前提的模块，按此模型重新标定。

## 核心链路：同意，但存储层不同
圣经 → 章节 → 一致性 → 存储 → 可视化，这条链是对的，我们逐段已有对应物：
- 圣经：worldBible（建故事时生成，contextFor 强制注入 + 紧凑化保预算）
- 章节：server/gemini.js 生成管线 + knowledge 模板 brief/beat
- 一致性：custom skill `storyweave-canon`（本日已建，含硬冲突/可疑两档）
- 存储：**线性章节序列 + 选择记录 + 季**，不是 DAG（见 23 条裁定）
- 可视化：剧情星图（已定为招牌，先在画风原型完成态露脸，全站版随新画风落地）

## 四个 ★ 模块
- **3 canon-consistency-checker ★**：同意优先级。已落地为技能；其「误报要分硬冲突/可疑两档」的提醒已并入技能输出格式；「已死角色又出场」类硬冲突列为必修。
- **6 crossover-merger ★**：部分同意。我们已有合流，但形态不同：是同平台双主角合流、主导侧裁决（代码硬规则），不是两个独立世界的三模式融合（平行宇宙/同一世界/嵌套）。三模式留作将来跨世界合流的候选设计，当前不做。其「先人工规则跑真实案例再自动化」与我们的现状一致——现行合流本就是硬规则。
- **16 branch-tree-visualizer ★**：同意做，但按我们的规模标定：单部作品的章节/选择/季星图（24–48 节点量级），没有它担心的千节点聚合问题；热度着色、折叠冷分支要等公开分享场景存在才有意义，缓办。
- **23 branch-data-model（DAG）★**：**不采纳**。DAG 是为任意分叉设计的数据结构；我们的故事是线性推进 + 章末选择记录 + 季扩展，硬套 DAG 只会给存档、迁移、合流全部加税。将来若真上线段落级分叉，再重开此议。它的「这个先定、后面都依赖它」恰恰说明它属于另一个产品。

## 合并成 5 个大 skill 的建议
方向与我们的合并裁定一致。我们的实际收敛是：产品代码承载（1/2/7/11/13/14/18/22）、一个 QA 技能（3/8/12/13 检测侧）、设计系统（15/16/17）、守卫（19/20 轻量/21）、未来候选（24/16 完整版/6 三模式）。不为清单完整性单独建技能文件。

## 结论
这份清单当评审意见价值高：补了注入防护（已做）、台账（已排进爽文批次）、随机按钮与 IP 明示（已排进画风落地）。当路线图则不成立：它的地基（DAG + 无限分支 + 融合生态）属于另一个产品。织界路线不变：爽文季播为纲，星图为招牌，一致性为护城河。
